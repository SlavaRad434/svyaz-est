# План реализации «СвязьЕсть»

Дата: 28 октября 2026 года. Статус: предложение для команды, не согласованный календарный план.

Основание: [требования](../svyaz-est-analysis.md) и [архитектура](architecture.md). В репозитории пока нет приложения, зависимостей, UI kit и автоматических проверок. План уточнён 28 октября: гостевые замеры без аккаунта участвуют в цвете, размер квадратов — 250×250 м; подробные контракты вынесены в [interfaces.md](interfaces.md).

В корне также изучены README, презентация и таблица требований. Архитектура прямо отдаёт приоритет обновлённым Markdown: старые материалы ещё содержат ручной ввод, отложенный speed test и другую трактовку цветов. Перед сдачей материалы нужно синхронизировать. Упомянутые `concept-and-requirements.md`, `pikpo_lab2_2026.pdf` и `svyaz-est-analysis-rf.xlsx` в текущем репозитории отсутствуют; план не предполагает, что их содержимое проверено.

## 1. Две точки готовности

**Учебный прототип:** запускаемое приложение с демонстрационной выборкой, настоящим расчётом оценок, навигацией, симуляцией измерений, ролей и сбоев. Режим явно помечен «Демо». Он позволяет проверить сценарии ЛР 2, но не подтверждает безопасность, качество измерений и готовность к публичному использованию.

**Публичный MVP:** тот же интерфейс с реальной авторизацией, измерительным сервером, БД, серверной проверкой, постоянной локальной очередью, модерацией и эксплуатационными проверками. Встроенный speed test и доставка после восстановления связи обязательны.

Начинаем с проверки способа сбора и общего ядра. Затем получаем законченный прототип и подключаем реальный сервер через тот же контракт. Технические эксперименты с измерениями выполняем до завершения интерфейса.

## 2. Решения перед основной разработкой

| Решение | Что сделать | Что зависит от результата |
|---|---|---|
| Автоматические метаданные | На целевых Android/iOS проверить доступность оператора, транспорта, VPN, технологии и условий. Зафиксировать источник каждого поля и случаи `unknown`. Проверять фактическую достоверность, а не только наличие API. | При текущих правилах неизвестный транспорт исключает запись из мобильного рейтинга. Если браузер не даёт нужных сведений, команда выбирает другую платформу сбора либо пересматривает охват. Ручной ввод не является обходным путём. Демо можно продолжать. |
| Гость и speed test | Решено: тест и отправка доступны гостю, `author_id = NULL`; гостевые замеры влияют на цвет. Технический токен отдельной попытки не является гостевым аккаунтом. | [Контракты](interfaces.md), nullable-связи, общие проверки и лимиты тестов. |
| Сбой до создания сессии | Определить контракт события без `testSessionId` и без геолокации, порядок доставки и серверной проверки. | Очередь должна фиксировать неуспешную попытку даже при недоступности сервера; без места событие не попадает на карту. |
| Территория и сетка | Решено: квадраты 250×250 м. Выбрать пилот, метрическую проекцию, начало и версию сетки. | Один `cellId` на клиенте и сервере; точные координаты не покидают устройство. |
| Вход и инфраструктура | Выбрать провайдера входа без собственной анкеты, место измерительного сервера и бюджет трафика. Для выбранных Яндекс Карт получить API-ключ, настроить ограничения по доменам и проверить условия использования и тариф перед публикацией. | Реальная интеграция, доступность сервиса и стоимость тестов. |
| Методика и время | Подтвердить стартовые параметры, часовой пояс суток, границы периода, допустимое расхождение часов и порядок выбора последнего замера при равном времени. | Воспроизводимые расчёты и дедупликация вклада автора. |
| Хранение и повторы | Определить срок очереди, тестовых сессий и ключей идемпотентности; согласовать приём результата после задержки доставки. Авторство фиксируется при старте теста и не меняется при смене аккаунта. | Отложенная отправка не должна теряться из-за истечения тестовой сессии или публиковаться от другого автора. |
| Макеты и UI kit | Предварительные [20 листов](wireframes/index.html) готовы; обсудить их по [листу согласования](wireframes/README.md) и проверить Mantine как кандидата. | Макеты ещё не согласованы командой; реализация UI начинается после фиксации решений. |

Эти решения фиксируются в ADR по факту согласования. Уже предложенные ADR не переводятся автоматически в статус «Принято».

## 3. Структура кода

```text
apps/web/              React, страницы, карта, измеритель, очередь, адаптеры
apps/api/              NestJS, авторизация, наблюдения, измерения, модерация
packages/contracts/   DTO, схемы валидации, ошибки, описание API
packages/domain/      чистые функции оценки, правила группировки, методика
docs/                 архитектура, ADR, макеты, протоколы проверок
```

Стек берётся из архитектуры как рабочее предложение: TypeScript, React + Vite, React Router, Яндекс Карты JavaScript API v3, NestJS, PostgreSQL + PostGIS. Выбор Яндекс Карт согласован пользователем 28 октября 2026 года. Версии и совместимость проверяются при создании проекта и закрепляются lock-файлом. Конкретные инструменты работы с БД и тестирования выбираются на этапе каркаса.

Карта подключается через `@yandex/ymaps3-reactify`; собственные ячейки отображаются полигонами `YMapFeature`, нажатие открывает карточку зоны. API-ключ передаётся через конфигурацию окружения. В этапе интерфейса проверяются загрузка API, ошибка и повторная попытка, отображение полигонов и обновление их цвета после изменения фильтров. Геокодер и маршрутизация в текущий объём не входят. Расчёт качества и данные наблюдений остаются независимыми от картографического API.

Клиент обращается к интерфейсу адаптера данных; демонстрационная и HTTP-реализации соблюдают один контракт. `packages/domain` не зависит от React, NestJS и БД. Публичные DTO отделяются от внутренних записей с автором и временем. Повторяющиеся значения, пороги и тексты выносятся в константы своего модуля. Бизнес-расчёты не размещаются в JSX.

## 4. Этапы и критерии готовности

| Этап | Работы | Проверяемый результат |
|---|---|---|
| 0. Проверка реализуемости | Эксперимент с метаданными и минимальными измерительными endpoints; решения из раздела 2. | Есть таблица фактически доступных данных на устройствах, ограничения измерителя и решение о платформе сбора. Возможность публичной операторской карты не считается доказанной до этого. |
| 1. Каркас | Workspace, приложения и общие пакеты, TypeScript, линтер, форматтер, сборка, тестовый раннер, CI, инструкция запуска. | Чистая установка и сборка воспроизводятся; проверки запускаются одной документированной последовательностью. |
| 2. Контракты | Наблюдения двух видов, фильтры, карточка, профили, права, тестовые сессии, квитанции, ошибки; OpenAPI и runtime-валидация. Определить неизвестные поля и происхождение метаданных. | Образцы валидных/невалидных запросов проверяются схемами. Успешный замер и событие ошибки нельзя перепутать. Сверены endpoints из архитектуры. |
| 3. Ядро оценки | Фильтрация по группе, сроку и статусу; исключение непригодного транспорта; один последний валидный вклад известного автора за сутки, один итог на гостевую попытку; достаточность, веса, средние и статусы. | Детерминированные тесты с фиксированным временем покрывают границы, старение, повторы, `unknown`, скрытые записи и отдельный счётчик ошибок. Карта и карточка используют один расчёт. |
| 4. Демонстрационный адаптер | Контрольные наборы, симулятор теста, имитация ролей, добавление, скрытие, восстановление, удаление и воспроизводимые сбои. | Изменение данных действительно меняет расчёт. Демо изолировано от реальных наблюдений и явно обозначено. |
| 5. Интерфейс прототипа | Карта и легенда, совместные фильтры, карточка, методика, запуск/отмена теста, результат, событие ошибки, мои записи, аккаунт, модерация. | Основные сценарии проходят целиком. Есть загрузка, ошибка, пустая и недостаточная выборка. Состояние карты сохраняется при возврате. Проверены ширины 360–1440 px, клавиатура и фокус. |
| 6. Постоянная локальная очередь | Хранилище IndexedDB как предложение, идентификатор операции до первой отправки, повтор при открытом приложении, восстановление после перезагрузки, проверка срока доставки и удаление ожидающей записи. | Разрывы до/после ответа, отказ хранилища и истечение срока токена попытки не дают ложного статуса «сохранено». Очередь привязана к попытке теста; автор необязателен и не меняется после входа. Повтор использует прежний ключ и содержимое. |
| 7. Сервер и БД | Миграции, сетка, справочники, аккаунты, сессии, наблюдения и детали, ключи операций, журнал модерации; внешний вход; проверка прав; приём и чтение данных. | Новая БД разворачивается миграциями. Параллельные повторы дают одну запись, тот же ключ с другим телом — `409`. Наблюдение и квитанция сохраняются атомарно. Публичный API выдаёт только агрегаты. |
| 8. Настоящие измерения | Сессия, download/upload/probe, некэшируемые ответы, счётчики трафика и времени, отмена, автоматическая геолокация в ячейку, серверная проверка результата. Подключение HTTP-адаптера. | Реальный тест укладывается в согласованный лимит трафика и 30 секунд; отмена останавливает передачу за ≤1 секунды в контролируемой среде. Ошибка не превращается в нулевую скорость. Результат проходит путь до карты через очередь. |
| 9. Модерация и удаление | Серверное скрытие/восстановление с причиной, аудит, пересчёт, удаление своих записей и аккаунта, правила резервных копий. | Чужие изменения запрещены. Скрытие и удаление меняют выдачу и агрегаты; восстановление БД не возвращает удалённые данные в активную выдачу. |
| 10. Пилотная приёмка | Реальные устройства и браузеры, нагрузка, полевые тесты, калибровка методики, резервное восстановление, инструкция эксплуатации. | Зафиксированы результаты NFR и ограничения. Выполнены критерии публичного MVP, демонстрационные данные отсутствуют в реальном рейтинге. |

Зависимости: этапы 1 → 2 → 3 → 4 → 5 дают основу прототипа. Этап 6 завершает сценарий надёжной доставки. После контрактов серверный этап 7 можно вести одновременно с интерфейсом; этап 8 зависит от эксперимента, сервера и очереди. Этапы 9–10 завершают публичный MVP. Если эксперимент требует смены платформы сбора, клиентскую часть плана нужно пересмотреть до основной реализации измерителя.

## 5. Что именно проверить в ядре

Стартовые параметры взяты из требований и остаются гипотезами до калибровки:

- Окно 30 дней, вес `2^(−возраст_в_днях/14)`.
- Не менее 5 учтённых замеров из разных тестовых сессий и 2 дат после всех исключений. Гостевые замеры участвуют в цвете; порог 3 аккаунтов отменён. Независимость гостевых авторов не подтверждается.
- Базовые задачи: download ≥1 Мбит/с, upload ≥0,5 Мбит/с, RTT ≤300 мс.
- Видеозвонок: download ≥5 Мбит/с, upload ≥3 Мбит/с, RTT ≤150 мс.
- Цвет по взвешенной доле прошедших замеров: зелёный ≥80%, жёлтый ≥50% и <80%, красный <50%. Недостаточная выборка всегда серая.
- Взвешенные средние считаются отдельно от цвета. Неизвестные значения не становятся нулями. События ошибок не входят в скоростные показатели.

Тестовые наборы: пустая выборка, один замер, минимально достаточная выборка, ровно пороговое значение и значения рядом с ним, повтор автора, граница суток и периода, старые/скрытые записи, только ошибки, неизвестный транспорт, смешанные условия. Для карты и карточки проверяется идентичность фильтров и результатов.

## 6. Приёмка и обязательные ограничения

- Нет редактируемой формы результата или ручной подстановки оператора, координат и условий. Геолокация недоступна — просмотр остаётся доступным, публикации на карте нет.
- Публичная выдача и логи не раскрывают точные координаты и авторов; публичная карточка показывает день последнего замера, а не точное время события.
- Сервер проверяет роли, владельца и сессии независимо от видимости кнопок. Отрицательные тесты охватывают прямые запросы и выход из аккаунта.
- Для очереди: 10 из 10 разрывов связи сохраняют запись при доступном хранилище; потеря ответа и конкурентная отправка не создают дублей. Закрытый браузер не обещает доставку.
- Карта различает ошибку загрузки и отсутствие наблюдений. Статусы подписаны текстом, действия имеют размер не менее 44×44 CSS px.
- Пересчёт после принятия или скрытия — ≤60 секунд. На профиле NFR-02: 100 тыс. записей, 50 читателей, API p95 ≤1 секунды, полезный экран ≤3 секунд в 75% запусков при 10 Мбит/с и RTT 100 мс.
- Перед пилотом проверяются резервное восстановление (RPO ≤24 ч, RTO ≤4 ч), удаление из активной БД ≤24 ч и из копий ≤30 дней.
- UI удаления — Should в таблице историй, но обработка удаления и ограничения NFR-05 обязательны. План включает UI, поскольку он также входит в экраны учебного прототипа.

Для ЛР 2 дополнительно готовятся структурная схема, use case, три activity-диаграммы, ER-модель, макеты, пять согласованных ADR и фактический отчёт об агенте. Коммит делается отдельным действием после проверки результата; этот план сам по себе не означает готовность этих артефактов.

## 7. Распределение работы и первый набор задач

Предлагаемое распределение для двух разработчиков: Максим — клиент, карта, экраны измерителя и локальная очередь; Вячеслав — API, БД, авторизация, измерительный сервер и модерация. Контракты, методика, эксперимент и приёмка — совместно. После фиксации контрактов клиент работает с демо-адаптером независимо от готовности сервера.

Первые небольшие изменения кода:

1. Технический эксперимент и запись результатов по метаданным и измерениям; решение о платформе.
2. Каркас workspace и команды установки, запуска, сборки, проверки типов и тестов.
3. Контракты наблюдений, карточки и тестовой сессии с согласованными спорными случаями.
4. `evaluateCell` и контрольные наборы с проверенными ожидаемыми результатами.
5. Демо-адаптер и первый законченный сценарий: карта → фильтр → карточка → объяснение оценки.
6. Симулятор теста → автоматический результат/событие ошибки → постоянная очередь → обновление карты.

Календарные сроки оцениваются после эксперимента и определения ближайшей цели: учебный прототип или публичный MVP. До этого точная оценка скрывала бы неопределённость платформы сбора. За пределами плана остаются маршрутизация, фоновый трекинг, офлайн-карта, вся страна и дополнительные профили. Сравнение операторов отдельной таблицей, редактор справочника и ссылки с фильтрами можно добавлять после обязательного объёма.
