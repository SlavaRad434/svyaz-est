# Отчёт по лабораторной работе 3. Финализация прототипа и защита

Дата: 15 ноября 2026 года. Команда: два разработчика. Ветка разработки: `lab3`.

ЛР 3 закрывает требования задания: финализация прототипа, реализация ключевых модулей
с покрытием 100% Must-have требований ЛР 1, выделенные паттерны GoF, UML-диаграммы
последовательности, тесты и рефакторинг. Роль агента отражена по факту работы.

## 1. Финализация прототипа и Must-have

На старте ЛР 3 проведён gap-анализ прототипа против Must-списка ЛР 1
(US-01–09, US-11, US-12, US-17). Выявлены три незакрытых требования, все реализованы:

| Требование | Было | Стало | Коммит |
|---|---|---|---|
| US-12: локальная очередь — результаты сохраняются до отправки, повтор без дубля | отправка шла напрямую, разрыв сети терял запись | `PendingQueue` (localStorage-адаптер): сохранение до доставки, повторы с теми же токеном и ключом, автодоставка при открытии приложения, счётчик и кнопка «Доставить сейчас» | `f341c6a` |
| US-09: модерация — список, скрытие/восстановление с причиной, журнал, отказ без роли | механизм в хранилище был, UI отсутствовал | панель `/admin`: таблица записей, причина строго из справочника, журнал решений (кто, когда, что, почему), явный отказ гостю и участнику | `ebdd03a` |
| US-05: вход без анкеты + FR-05.2 выход | имитация только переключателем роли | экран `/login`: кнопка провайдера, состояния ожидания и ошибки, выход; в шапке «Войти»/«Мои записи» по роли | `aeb2cb3` |

Should-требование US-10 («Мои записи», удаление вклада и аккаунта) закрыто бонусом
в том же коммите: список своих записей, удаление с подтверждением, удаление аккаунта
с завершением сессии, журнал удалений для повторного исключения после бэкапа.

Итог: **все 12 Must-историй представлены в прототипе**; US-17 (встроенный тест) работает
на симуляторе измерений — реальный измерительный сервер вынесен в публичный MVP по
плану ЛР 2 (этап 8) и требует отдельного согласования объёма.

## 2. Паттерны GoF в коде

### 2.1. Strategy — адаптеры данных и хранилища

```ts
// packages/contracts/src/gateway.ts
export interface DataGateway {
  getMapCells(filters: CellFilters, bbox?: Bbox): Promise<MapCellsResponse>;
  submitObservation(input, token, idempotencyKey): Promise<ObservationReceipt>;
  /* ... */
}

// apps/web/src/lib/queue.ts
export interface QueueStorageAdapter {
  read(): string | null;
  write(value: string): void;
}
export class LocalStorageAdapter implements QueueStorageAdapter { /* ... */ }
export class InMemoryAdapter implements QueueStorageAdapter { /* ... */ }
```

Весь UI работает с интерфейсом `DataGateway`, не зная, за ним демо-адаптер на
демонстрационных данных или HTTP-клиент к NestJS-серверу. Это позволяет разрабатывать
интерфейс до готовности сервера и подменять реализацию без изменения компонентов
(ADR-002). Тот же паттерн в очереди: `LocalStorageAdapter` для приложения и
`InMemoryAdapter` для тестов.

### 2.2. Observer — хранилища с подпиской

```ts
// apps/web/src/demo/DemoStore.ts
subscribe(listener: () => void): () => void {
  this.listeners.add(listener);
  return () => this.listeners.delete(listener);
}
private emit(): void { /* version += 1; listeners... */ }

// компоненты:
const storeVersion = useSyncExternalStore(
  (listener) => demoStore.subscribe(listener),
  () => demoStore.snapshotVersion,
);
```

`DemoStore` и `PendingQueue` уведомляют подписчиков о каждом изменении; React через
`useSyncExternalStore` перерисовывает карту, карточку, панель модерации и счётчик
очереди. Что даёт: данные меняются в одном месте (в том числе фоновая доставка
очереди), а все экраны остаются согласованными без ручной рассылки событий.

### 2.3. State — машина фаз экрана теста

```ts
// apps/web/src/pages/TestPage.tsx
type Phase =
  | { name: 'idle' }
  | { name: 'creating' }
  | { name: 'running'; stage: DemoTestStage }
  | { name: 'submitting' }
  | { name: 'done'; result: DemoTestResult; receipt: ObservationReceipt | null;
      submitError: string | null; pending: number };
```

Каждое состояние экрана теста описано отдельным вариантом типа с обязательными
данными фазы; недостижимые сочетания (например, «результат» без квитанции и счётчика
очереди) исключены на уровне компиляции. Что даёт: переходы явные, UI-ветки строго
соответствуют фазе, отмена и сбой не приводят к «зависшим» состояниям.

Дополнительно в коде присутствуют Singleton (`demoGateway` — единственный экземпляр
шлюза приложения, `apps/web/src/lib/demo.ts`) и Factory Method (`createLeafletMap` —
сборка карты за интерфейсом `MapHandle`).

## 3. Рефакторинг

| Изменение | Почему |
|---|---|
| `DemoStore.addAll()` для демо-сида (было: цикл `add()`) | `add()` копирует массив на каждую вставку — O(N²) на ~20 тыс. записей сида; `addAll` — одна копия и одно уведомление |
| Кэш группировки наблюдений по паре (размер клетки, версия хранилища) в `DemoGateway` | перегруппировка 20 тыс. наблюдений выполнялась на каждый шаг панорамирования; теперь только при смене масштаба или данных |
| Выделен `lib/delivery.ts` (`flushPendingQueue`) | одна точка доставки очереди для автоповтора при старте и для экрана теста — без дублирования логики токенов |
| `ZoneCardContent` выделен из `ZoneCard` | один и тот же контент карточки работает в доке (десктоп) и в нижнем Drawer-е (мобильные) |
| Единые подписи сетей и условий в `lib/labels.ts` | коды (`4g`, `outdoor`) больше не показываются пользователю напрямую |
| Точечный класс `.tap-target` (44 px) вместо глобального правила на все кнопки | служебные кнопки xs перестали растягиваться; правило доступности осталось на главных действиях |
| Динамическая сетка карты: ребро из ширины видимой области (~10 колонок) вместо фиксированного окна 25×25 клеток 250 м | сетка покрывает весь экран на любом масштабе; данные перегруппировываются по геометрии с базовой решётки |

В ходе интеграционного тестирования агентом был найден и исправлен дефект ремапа
данных на динамической решётке: в группы попадали наблюдения со старым значением
`cellId`, а `evaluateCell` сверяет идентификатор — карта оставалась серой. Исправление:
в группу кладётся копия наблюдения с переписанным `cellId` (покрыто тестами).

## 4. Тестирование

С использованием агента написаны модульные и интеграционные тесты (Vitest).
Итог: **56 тестов, все зелёные**; typecheck и сборка без ошибок.

- Модульные (56): методика оценки и границы порогов (30), сетка и проекция (11),
  очередь US-12 (5): сохранение до доставки, восстановление после перезагрузки,
  счётчик попыток и причина ошибки, неизменность токена и ключа.
- Интеграционные (10, `gateway.integration.test.ts`): повтор отправки без дубля
  (NFR-07), авторство гостя зафиксировано при создании сессии и не меняется после
  входа (US-05), скрытие модератором уменьшает выборку (US-08), очередь при разрыве
  сети и доставка без дублей (US-12), отказ в модерации без роли (NFR-04), журнал
  решений и восстановление, состав админ-списка, свои/чужие удаления, удаление
  аккаунта, запреты для гостя.

Edge cases покрыты: повтор с тем же ключом, разрыв сети до и после сохранения,
чужое удаление, не-админ в модерации, повреждённое хранилище очереди, пустая ячейка.

## 5. Роль агента

Задачи, делегированные агенту на ЛР 3: gap-анализ прототипа против Must-списка ЛР 1;
реализация очереди US-12, панели модерации US-09, экрана входа US-05 и раздела
«Мои записи» US-10; написание модульных и интеграционных тестов; рефакторинг
производительности (addAll, кэш группировки) и вёрстки (пересечения слоёв карты,
мобильная карточка зоны).

Как проверялись результаты: интеграционные тесты на реальном `DemoGateway` (а не
моках), ручной прогон сценариев в браузере со скриншотами (гость → отказ в модерации;
админ → скрытие с причиной; разрыв сети → очередь → доставка), `tsc --noEmit` и сборка.
Найденные агентом проблемы: дефект ремапа `cellId` (серая карта), несовпадение
формата времени с контрактом (`instant` требует миллисекунды), ключ в `.env.example`
(удалён до коммита).

## 6. Ограничения и перспективы

- Измерение скорости — симулятор; реальный измерительный сервер — этап 8 плана
  публичного MVP (probe/download/upload с лимитами и серверной проверкой).
- Вход имитируется локальной ролью; реальный OAuth-провайдер — этап 7 (сервер).
- Очередь хранится в localStorage; для MVP — IndexedDB с тем же интерфейсом адаптера.
- Агрегаты пересчитываются на лету; при росте объёма — материализованный кэш
по версии методики.
