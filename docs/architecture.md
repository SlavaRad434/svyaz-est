# СвязьЕсть — проработка лабораторной работы 2

Дата: 14 октября 2026 года. Команда: два разработчика.

Статус: проект решений для обсуждения перед реализацией. Согласование команды, готовый код и проведённые испытания пока не заявляются. ADR имеют статус «Предложено»; после согласования перед сдачей их необходимо перевести в «Принято», как требует задание.

Для «СвязьЕсть» предлагается мобильное веб-приложение с картой, ручным добавлением замеров и объяснимой оценкой качества связи. Архитектура — клиент и модульный сервер с одной БД. Для ЛР 2 предлагается исполнимый прототип на демонстрационных данных, показывающий основные сценарии и ошибки.

## 1. Структурная схема системы

Предлагаемое разбиение:

```text
Браузер пользователя
├── Карта, фильтры и карточка зоны
├── Вход и регистрация
├── Добавление замера и жалобы
├── Мои записи и удаление аккаунта
├── Панель модерации
└── Клиент API
          │ HTTPS / JSON
          ▼
Сервер приложения
├── Авторизация и права доступа
├── Приём и проверка наблюдений
├── Расчёт оценок и достаточности данных
├── Модерация и журнал решений
├── Удаление пользовательских данных
└── Справочники и версии методики
          │
          ▼
PostgreSQL + PostGIS
```

Отдельная внешняя зависимость — поставщик картографической подложки. Геокодер потребуется при реализации поиска адресов US-15.

| Компонент | Ответственность | Связь с требованиями |
|---|---|---|
| Карта и карточка | Показать зоны, фильтры, показатели и объяснение статуса | US-01–04, US-11 |
| Авторизация | Управлять сессиями и проверять права | US-05, NFR-04 |
| Наблюдения | Принимать замеры и жалобы, проверять поля, исключать повторную запись запроса | US-06–07, NFR-07 |
| Оценка | Фильтровать, исключать повторы, рассчитывать достаточность и статус | US-08, NFR-08 |
| Модерация | Скрывать и восстанавливать записи с причиной | US-09 |
| Управление данными | Удалять собственные записи и аккаунт | US-10, NFR-05 |
| Справочники | Хранить операторов, профили задач и методику | US-02–03, US-14 |

Модульный монолит позволяет двум разработчикам запускать, тестировать и сопровождать один сервер. Разделение на модули сохраняет границы ответственности без отдельных сервисов, очередей и распределённых транзакций.

Правило взаимодействия слоёв:

```text
HTTP-контроллер → прикладной сервис → бизнес-правила → репозиторий → БД
```

Расчёт оценок не должен находиться в React-компонентах или HTTP-контроллерах.

Интерфейс можно показать до завершения сервера. Прототип с имитацией входа не подтверждает выполнение требований безопасности и нагрузочных NFR.

## 3. UML — варианты использования и три активности

Для итогового документа необходимо оформить настоящие UML-диаграммы, например в PlantUML. Ниже определено их содержание; текстовые сценарии не заменяют готовые UML-диаграммы.

### 3.1. Диаграмма вариантов использования

| Актор | Доступные действия |
|---|---|
| Гость | Смотреть карту, менять фильтры, выбирать профиль, открывать карточку, читать методику, регистрироваться и входить |
| Участник | Все действия гостя; добавлять замер и жалобу, смотреть и удалять свои записи, удалять аккаунт, выходить |
| Администратор | Действия участника; просматривать записи для модерации, скрывать и восстанавливать их, смотреть журнал |

На диаграмме участник наследует возможности гостя, администратор — участника.

Связи:

- «Добавить замер» включает проверку полей и сохранение наблюдения.
- «Получить оценку зоны» включает проверку достаточности данных.
- «Скрыть запись» и «Восстановить запись» включают запись решения в журнал и обновление оценки.
- «Удалить свой вклад» включает проверку владельца и обновление оценки.

Вход является предусловием защищённых действий: пользователь с действующей сессией не проходит его заново при каждой публикации.

### 3.2. Основной сценарий — выбрать место для видеозвонка

Дорожки: пользователь, интерфейс, сервер.

1. Пользователь открывает карту.
2. Интерфейс загружает пилотную территорию и справочники.
3. Пользователь выбирает оператора, сеть, период, условия и профиль «Видеозвонок».
4. Сервер формирует соответствующую выборку.
5. Сервер проверяет достаточность данных.
6. Если выборка достаточна — рассчитывает оценку; иначе возвращает серый статус с причиной.
7. Интерфейс показывает зоны.
8. Пользователь открывает карточку.
9. Карточка показывает показатели, период, число записей и ограничения оценки.

Результат: пользователь получает предварительную оценку либо понимает, почему её пока нет.

### 3.3. Альтернативный сценарий — сообщить о проблеме позже

1. Пользователь сталкивается с проблемой связи.
2. После восстановления доступа открывает сервис.
3. Входит в аккаунт.
4. Выбирает «Сообщить о проблеме».
5. Указывает место, оператора, время события, условия и тип проблемы.
6. Сервер проверяет поля и сохраняет жалобу.
7. Интерфейс показывает подтверждение.
8. Жалоба учитывается в отдельном слое.

Результат: сообщение относится к моменту проблемы, а не к моменту отправки. Оно не превращается в замер со скоростью ноль. Сценарий покрывает Must US-07 и не требует реализации локальных черновиков.

### 3.4. Исключение — ответ на отправку замера потерян

1. Участник заполняет форму.
2. Клиент создаёт идентификатор операции и отправляет запрос.
3. Возможны две ветви: сервер успел сохранить запись либо запрос не дошёл.
4. Клиент не получает подтверждение.
5. Интерфейс сообщает: «Не удалось подтвердить отправку», сохраняя введённые данные.
6. Пользователь повторяет отправку.
7. Клиент использует тот же идентификатор операции.
8. Сервер возвращает уже созданную запись либо сохраняет её впервые.
9. Интерфейс показывает одно подтверждение.

Результат: повтор не создаёт дубль. Сценарий проверяет NFR-07.

## 4. ER-модель — сущности, атрибуты и связи

Предлагается общая сущность наблюдения и отдельные данные замера и жалобы.

| Сущность | Основные атрибуты |
|---|---|
| `users` | `id PK`, `email UNIQUE`, `password_hash`, `role`, `created_at` |
| `sessions` | `id PK`, `user_id FK`, `token_hash`, `expires_at`, `revoked_at` |
| `operators` | `id PK`, `name`, `is_active` |
| `grid_cells` | `id PK`, `geometry`, `grid_version` |
| `observations` | `id PK`, `author_id FK`, `cell_id FK`, `operator_id FK nullable`, `kind`, `occurred_at`, `submitted_at`, `environment`, `status` |
| `measurement_details` | `observation_id PK/FK`, `network_type`, `transport`, `download_mbps`, `upload_mbps`, `rtt_ms`, `source`, `input_method` |
| `complaint_details` | `observation_id PK/FK`, `problem_type` |
| `methodology_versions` | `id PK`, `version UNIQUE`, `window_days`, `half_life_days`, `min_samples`, `min_authors`, `min_dates`, `effective_from` |
| `task_profiles` | `id PK`, `methodology_id FK`, `code`, `name`, `min_download`, `min_upload`, `max_rtt` |
| `moderation_actions` | `id PK`, `observation_id FK`, `moderator_id FK`, `action`, `reason`, `created_at` |
| `idempotency_requests` | `id PK`, `user_id FK`, `operation`, `key`, `payload_hash`, `result_id`, `created_at` |
| `deletion_events` | `id PK`, `target_type`, `target_id`, `requested_at`, `completed_at`, `purge_after` |

Связи для ER-диаграммы:

```text
users        1 ─── N sessions
users        1 ─── N observations
operators    1 ─── N observations
grid_cells   1 ─── N observations

observations 1 ─── 0..1 measurement_details
observations 1 ─── 0..1 complaint_details
observations 1 ─── N moderation_actions
users        1 ─── N moderation_actions

methodology_versions 1 ─── N task_profiles
users                1 ─── N idempotency_requests
```

Со стороны наблюдения связь с оператором необязательная: для неизвестного оператора `operator_id = NULL`.

Ограничения:

- У наблюдения существует ровно один соответствующий типу набор деталей.
- Неизвестный оператор — `NULL`, неизвестная технология — отдельное значение.
- Скорости и RTT неотрицательны; пропуск не равен нулю.
- Время события не может быть в будущем.
- Комбинация `user_id + operation + key` уникальна.
- Причина модерации обязательна.
- Точные пользовательские координаты в БД не поступают: браузер определяет ячейку до отправки.
- Сутки для исключения повторов считаются в зафиксированном часовом поясе пилота; сами моменты времени хранятся в UTC.

Журнал удалений нужен, чтобы после восстановления резервной копии повторно исключить удалённые данные. Его сроки хранения и очистку нужно согласовать с политикой резервных копий.

Агрегаты первоначально рассчитываются из наблюдений. Отдельный кэш вводится только при необходимости по результатам измерений. Это уменьшает риск расхождения карты и карточки.

## 5. Программные интерфейсы и контракты

Базовый путь: `/api/v1`.

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `GET /catalog` | Операторы, профили, версия методики | Все |
| `GET /map/cells` | Геометрия и оценки зон по фильтрам | Все |
| `GET /cells/{id}/summary` | Подробная карточка зоны | Все |
| `POST /auth/register` | Регистрация | Гость |
| `POST /auth/login` | Создание сессии | Гость |
| `POST /auth/logout` | Завершение сессии | Участник |
| `GET /me` | Текущий пользователь | Участник |
| `POST /measurements` | Добавление замера | Участник |
| `POST /complaints` | Добавление жалобы | Участник |
| `GET /me/observations` | Собственные записи | Участник |
| `DELETE /me/observations/{id}` | Удаление собственной записи | Владелец |
| `DELETE /me` | Запрос удаления аккаунта | Владелец после подтверждения |
| `GET /admin/observations` | Список для модерации | Администратор |
| `POST /admin/observations/{id}/moderation` | Скрытие или восстановление | Администратор |
| `GET /admin/moderation-actions` | Журнал решений | Администратор |

Общие фильтры карты и карточки:

```text
operatorId
networkType
environment
periodFrom
periodTo
profileCode
```

У карты дополнительно есть границы видимой области `bbox`. Для прототипа один расчёт выполняется для одной группы оператора, технологии и условий: интерфейс не создаёт ложного общего статуса из несопоставимых измерений.

### 5.1. Добавление замера

```json
{
  "cellId": "pilot-cell-0042",
  "operatorId": "operator-1",
  "occurredAt": "2026-10-14T10:30:00Z",
  "networkType": "4g",
  "transport": "mobile",
  "environment": "outdoor",
  "downloadMbps": 12.4,
  "uploadMbps": 4.8,
  "rttMs": 82,
  "source": "Внешний тест, указанный пользователем",
  "inputMethod": "manual"
}
```

Идентификатор повторяемой операции передаётся заголовком `Idempotency-Key`. Тот же ключ с другим содержимым возвращает `409 Conflict`.

### 5.2. Ответ карточки

Ответ должен содержать:

```text
cellId
filters
methodologyVersion
calculatedAt
status
reasonCodes
sampleCount
lastMeasurementDate
metrics
complaintCount
```

Статусы: `green`, `yellow`, `red`, `insufficient_data`. Отдельный код причины различает отсутствие записей и недостаточную выборку.

Публичный ответ не содержит авторов и точного времени отдельных событий. При отсутствии показателя возвращается `null`.

### 5.3. Единый формат ошибки

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Проверьте поля формы",
  "fieldErrors": {
    "occurredAt": "Время измерения не может быть в будущем"
  },
  "requestId": "request-123"
}
```

### 5.4. Основные сигнатуры бизнес-логики

```ts
evaluateCell(input: EvaluationInput): CellSummary;

createMeasurement(
  actor: AuthenticatedUser,
  input: CreateMeasurementInput,
  idempotencyKey: string
): Promise<MeasurementReceipt>;

moderateObservation(
  actor: AdminUser,
  observationId: string,
  decision: ModerationDecision
): Promise<void>;
```

`evaluateCell` получает фиксированное время расчёта и версию методики. Это позволяет воспроизводить результаты в тестах.

## 6. Wireframe-ы и экранные формы

До начала программирования команда согласует расположение блоков, навигацию и состояния.

| Экран | Содержание | Переходы |
|---|---|---|
| Карта | Фильтры, профиль задачи, зоны, легенда, кнопки добавления | Карточка, вход, формы |
| Карточка зоны | Статус, показатели, период, выборка, условия, жалобы, объяснение | Карта, методика, добавление |
| Вход / регистрация | Поля, ошибки, переключение режима | Возврат к исходному действию |
| Добавление замера | Место, оператор, сеть, время, условия, источник, показатели | Подтверждение, карта |
| Жалоба | Место, оператор, время события, условия, тип проблемы | Подтверждение, карта |
| Мои записи | Замеры и жалобы, состояния, удаление | Карточка, подтверждение удаления |
| Настройки аккаунта | Удаление аккаунта, выход | Подтверждение, карта |
| Модерация | Список, фильтр, детали записи, причина решения | Журнал и карта |
| Методика | Пороги, достаточность, ограничения | Назад |

Композиция основной страницы на компьютере:

```text
┌─────────────────────────────────────────────────────┐
│ СвязьЕсть                      Мои записи / Войти   │
├────────────────┬────────────────────────────────────┤
│ Оператор       │                                    │
│ Тип сети       │               Карта                │
│ Период         │                                    │
│ Условия        │                         Легенда    │
│ Профиль задачи ├────────────────────────────────────┤
│                │ Карточка выбранной зоны            │
├────────────────┴────────────────────────────────────┤
│ Добавить замер          Сообщить о проблеме          │
└─────────────────────────────────────────────────────┘
```

На смартфоне:

- Фильтры открываются отдельной панелью.
- Карточка появляется снизу.
- Формы занимают отдельный экран.
- Состояние карты и фильтров сохраняется при возврате.
- На ширине 360 px страница не прокручивается горизонтально.
- Статус всегда сопровождается текстом.

Для каждого wireframe нужны состояния загрузки, успешного результата, недостаточных данных и ошибки. Ошибка загрузки не должна выглядеть как пустая выборка.

При согласовании команда отдельно подтверждает понятность серого статуса, различие жалобы и замера, расположение действий и поведение возврата из формы. Для сдачи необходимо подготовить wireframe-ы всех основных экранов, а не только приведённую композицию карты.

## 7. Интерактивный прототип и работа с агентом

### 7.1. Объём прототипа

- Все перечисленные основные экраны.
- Рабочие переходы между ними.
- Фильтры, меняющие отображаемые данные.
- Реальная реализация правил оценки на демонстрационной выборке.
- Проверка полей форм.
- Добавление и удаление демонстрационных наблюдений.
- Скрытие и восстановление записи с изменением оценки.
- Имитация гостя, участника и администратора.
- Воспроизводимая ошибка отправки и повтор без дубля.
- Явная надпись «Демо».

Для методики используются параметры из ЛР 1: окно 30 дней, полураспад веса 14 дней, минимум 5 замеров от 3 аккаунтов за 2 даты. Эти значения остаются проектными допущениями.

| Граничные значения | Корректность порогов профиля |
| Повторы автора | Один учитываемый вклад за сутки |

| Только жалобы | Отсутствие искусственных нулевых замеров |

### 7.4. Отчёт об агенте

Отчёт ведётся по фактической работе.

| Поле | Что фиксировать |

## 8. Архитектурные решения ADR

В задании итоговые ADR должны иметь статус «Принято». Сейчас их статус — «Предложено»; после согласования команда переводит их в «Принято».

### ADR-001: Модульный монолит для серверной части

**Статус:** Предложено.

**Контекст:** US-05–10 требуют связанных операций с аккаунтами, наблюдениями, модерацией и удалением. NFR-10 требует сопровождаемости. Команда состоит из двух разработчиков.

**Рассмотренные альтернативы:**

1. Микросервисы — увеличивают затраты на инфраструктуру и согласованность.
2. Единый сервер без модульных границ — затрудняет сопровождение.
3. Только клиент — не обеспечивает доверенную проверку прав.

**Принятое решение:** Предлагается один сервер с модулями авторизации, наблюдений, оценки, модерации и управления данными. Контроллеры вызывают сервисы, сервисы используют репозитории.

**Последствия:** Проще запуск и транзакции. Требуется соблюдать границы модулей. Масштабирование сначала выполняется для приложения целиком.

**Роль агента:** Агент предложил разбиение и сопоставил варианты с размером команды. Корректировки студентов пока не зафиксированы.

### ADR-002: React и TypeScript с подменяемым адаптером данных

**Статус:** Предложено.

**Контекст:** US-01–04 и US-11 требуют интерактивной карты и адаптивных экранов. ЛР 2 требует запускаемого прототипа с навигацией.

**Рассмотренные альтернативы:**

1. Статические HTML-страницы — сложнее поддерживать общие состояния.
2. Нативное приложение — расширяет объём разработки.
3. Приложение с серверным рендерингом — добавляет ненужный для выбранного прототипа слой.

**Принятое решение:** Предлагаются React-компоненты на TypeScript, доступ к данным через интерфейс адаптера и методика оценки в отдельном модуле.

**Последствия:** Интерфейс можно разрабатывать независимо от API. Нужно контролировать соответствие демонстрационного и HTTP-адаптеров. Локальная имитация ролей не обеспечивает безопасность.

**Роль агента:** Агент предложил разделить интерфейс, контракты и расчёт. Выбор UI kit и корректировки команды ещё не подтверждены.

### ADR-003: PostgreSQL с PostGIS и хранение ячеек вместо точных координат

**Статус:** Предложено.

**Контекст:** US-06–10 требуют связанных данных, агрегации, модерации и удаления. NFR-05 запрещает сохранение точных пользовательских координат.

**Рассмотренные альтернативы:**

1. JSON-файлы — неудобны для конкурентной записи и связей.
2. SQLite — допустим для локальной демонстрации, но для целевого многопользовательского сервера выбирается отдельная БД.
3. Документная БД — не даёт явного преимущества для этой связанной модели.

**Принятое решение:** Предлагаются реляционные таблицы наблюдений и их деталей, геометрия ячеек в PostGIS. Браузер отправляет `cellId`. Изменения схемы выполняются миграциями.

**Последствия:** Проще контролировать целостность. Требуется настройка БД и пространственной сетки. Ячейка снижает точность местоположения, но не доказывает полную анонимность.

**Роль агента:** Агент предложил модель и связал её с приватностью. Выбор территории и параметров сетки остаётся за командой.

### ADR-004: REST API и идемпотентная запись наблюдений

**Статус:** Предложено.

**Контекст:** US-06–07 и NFR-07 требуют надёжной отправки при нестабильной сети. NFR-10 требует явных контрактов.

**Рассмотренные альтернативы:**

1. GraphQL — дополнительная сложность при небольшом числе операций.
2. WebSocket как основной транспорт — постоянное соединение не требуется.
3. POST без ключа операции — создаёт риск дублей после потери ответа.

**Принятое решение:** Предлагаются HTTPS, REST и JSON, OpenAPI, идемпотентный ключ для публикации, сохранение наблюдения и результата операции в одной транзакции.

**Последствия:** Повторная отправка предсказуема. Нужно хранить ключи, проверять содержимое повторов и определить срок их хранения. Конкурентные повторы требуют отдельного теста.

**Роль агента:** Агент предложил сценарий потери ответа и соответствующий контракт. Фактические результаты реализации и проверки дополнят ADR.

### ADR-005: Версионированная оценка и раздельный учёт жалоб

**Статус:** Предложено.

**Контекст:** US-03, US-04 и US-08 требуют объяснимой оценки. US-07 запрещает интерпретировать жалобу как нулевой замер. NFR-08 требует воспроизводимости.

**Рассмотренные альтернативы:**

1. Цвет по среднему download — игнорирует upload, RTT и достаточность.
2. Последняя запись — чрезмерно зависит от одного наблюдения.
3. Жалоба как нулевая скорость — искажает количественные данные.

**Принятое решение:** Предлагаются фильтрация по группе и периоду, исключение повторных вкладов, проверка достаточности и взвешенная доля замеров, прошедших профиль. Жалобы показываются отдельно. Ответ содержит версию методики и время расчёта.

**Последствия:** Результат можно объяснить и проверить. Необходимы тесты границ и старения. На старте карта может содержать много серых зон. Пороги требуют полевой калибровки.

**Роль агента:** Агент перенёс методику ЛР 1 в архитектурные правила и предложил проверочные наборы. Изменений порогов студентами пока нет.

## 9. Порядок выполнения и критерий готовности

1. Зафиксировать границы прототипа, способ входа и демонстрационную территорию.
2. Оформить структурную схему, UML и ER-модель.
3. Согласовать wireframe-ы в команде.
4. Зафиксировать контракты и пять ADR.
5. Реализовать расчёт и демонстрационные данные.
6. Реализовать экраны и навигацию.
7. Проверить три сценария, пограничные данные, мобильную компоновку и клавиатуру.
8. Дополнить отчёт реальными промптами и корректировками.
9. Сохранить документацию и код в одном репозитории и сделать итоговый коммит.

Для защиты должны быть готовы:

- Архитектурный документ со структурной схемой и обоснованием стека.
- Одна use case-диаграмма.
- Три activity-диаграммы.
- ER-диаграмма с атрибутами, ключами и связями.
- Описание программных интерфейсов.
- Согласованные wireframe-ы.
- Пять согласованных ADR со статусом «Принято».
- Запускаемый прототип с навигацией.
- Отчёт о работе с агентом.
- Итоговый коммит в общем репозитории курса.

Отправка на GitHub не обязательна по заданию: локальный репозиторий с историей и коммитом подходит.
