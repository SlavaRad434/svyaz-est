# СвязьЕсть — проработка лабораторной работы 2

Дата: 14 октября 2026 года. Команда: два разработчика.

Статус: проект решений для обсуждения перед реализацией. Согласование команды, готовый код и проведённые испытания пока не заявляются. ADR имеют статус «Предложено»; после согласования перед сдачей их необходимо перевести в «Принято», как требует задание.

Для «СвязьЕсть» предлагается мобильное веб-приложение с картой, автоматическим сбором замеров и объяснимой оценкой качества связи. Архитектура — клиент и модульный сервер с одной БД. Для ЛР 2 предлагается исполнимый прототип на демонстрационных данных, показывающий основные сценарии и ошибки.

Границы MVP с учётом уточнения пользователя от 14 октября 2026 года:

- Один город или несколько районов.
- Просмотр, запуск теста и отправка наблюдений доступны гостю и участнику. У гостевого наблюдения `author_id = NULL`; скрытый гостевой аккаунт не создаётся. Вход нужен для истории аккаунта и управления его данными.
- Два профиля: «Базовые задачи» и «Видеозвонок».
- Все данные наблюдений заполняются автоматически. Пользователь запускает тест и разрешает доступ к геолокации; поля для ручного ввода или исправления показателей отсутствуют.
- События неуспешных тестов фиксируются автоматически и существуют отдельно от измерений скорости; форма ручной жалобы не предусмотрена.
- Недостаток данных обозначается серым статусом.
- Встроенный speed test входит в Must MVP (US-17, NFR-11). Маршрутизация остаётся за пределами пилота.
- Автоматическое сохранение и отправка после восстановления связи — Must (US-12). Результаты тестов и события ошибок сохраняются на устройстве до успешной отправки; полноценная офлайн-карта пока не входит в требования.

Решение пользователя об автоматическом заполнении заменяет прежнее предложение ручного переноса результатов. XLSX и презентация пока содержат предыдущую редакцию и требуют отдельной синхронизации с обновлёнными Markdown-документами.

### Автоматическое заполнение и ограничения платформы

Пользователь не заполняет анкеты и параметры наблюдений. Допустимы нажатия кнопок, выбор фильтров просмотра и системные разрешения; они не заменяют сбор данных. Для входа предлагается кнопка внешнего провайдера с автоматическим созданием локального профиля, без собственной формы регистрации. Конкретный провайдер ещё не выбран; его требования к входу проверяются отдельно.

| Данные | Автоматический источник | Если получить не удалось |
|---|---|---|
| Download, upload, прикладной RTT | Встроенный тест к измерительному серверу | Событие ошибки, без нулей и ручной подстановки |
| Место | Geolocation API с разрешения, преобразование в ячейку на устройстве | Просмотр доступен, публикация замера на карте недоступна |
| Время | Часы устройства с серверной проверкой; время приёма задаёт сервер | Некорректная запись отклоняется, исправления от пользователя не требуются |
| Источник и метод | Конфигурация тестовой сессии, версия измерителя | Запись без обязательной версии метода отклоняется |
| Оператор и радиотехнология | Только проверенный автоматический источник на поддерживаемой платформе | null / unknown; не приписывать запись конкретному оператору |
| Транспорт и VPN | Доступные платформенные признаки с указанием происхождения | unknown; запись исключается из мобильного рейтинга |
| Помещение или улица | Только надёжный автоматический источник, если он доступен | unknown; ручной вопрос отсутствует |

Браузерный [Network Information API](https://developer.mozilla.org/en-US/docs/Web/API/NetworkInformation) имеет ограниченную поддержку; effectiveType основан на скорости и задержке и не доказывает реальную технологию 4G/5G. Этот API не даёт гарантированного определения оператора, VPN или помещения. [Geolocation API](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation_API) требует разрешения пользователя. Определять оператора SIM только по внешнему IP не предполагается.

До публичного пилота обязателен технический эксперимент: достаточно ли автоматически доступных данных для карты операторов. Если нет, требуется клиент на платформе с подходящими API и проверкой разрешений либо пересмотр охвата. Нативный клиент сам по себе не гарантирует все поля. Ручной ввод не является резервным решением. Автоматический сбор выполняется в рамках явно запущенного теста, без фонового трекинга.

Измерительный сервер ограничивает длительность и объём сессии, использует некэшируемые тестовые ответы и проверяет токен конкретной попытки теста; аккаунт у тестовой сессии необязателен. Клиентский результат всё равно требует серверной проверки и защиты от подделки. Локальная очередь хранит ячейку, автоматически собранный результат, идентификаторы попытки и операции и токен попытки; доставляет запись при открытом приложении. Гостю вход не требуется. Авторство фиксируется при создании тестовой сессии и не меняется после входа или выхода. При отказе локального хранилища интерфейс явно сообщает, что запись не сохранена.

## 1. Структурная схема системы

Предлагаемое разбиение:

```text
Браузер пользователя
├── Карта, фильтры и карточка зоны
├── Вход и регистрация
├── Запуск теста и автоматическое определение доступных данных
├── Локальная очередь результатов и событий ошибок
├── Мои записи и удаление аккаунта
├── Панель модерации
└── Клиент API
          │ HTTPS / JSON
          ▼
Сервер приложения
├── Авторизация и права доступа
├── Приём и проверка наблюдений
├── Управление тестовыми сессиями и измерительные endpoints
├── Расчёт оценок и достаточности данных
├── Модерация и журнал решений
├── Удаление пользовательских данных
└── Справочники и версии методики
          │
          ▼
PostgreSQL + PostGIS
```

Отдельная внешняя зависимость — Яндекс Карты JavaScript API v3: подложка и отображение собственных полигонов ячеек. Выбор согласован пользователем 28 октября 2026 года. Выбор места для просмотра выполняется на карте или по текущей геопозиции без ввода адреса.

| Компонент | Ответственность | Связь с требованиями |
|---|---|---|
| Карта и карточка | Показать зоны, фильтры, показатели и объяснение статуса | US-01–04, US-11 |
| Авторизация | Управлять сессиями и проверять права | US-05, NFR-04 |
| Наблюдения | Принимать автоматически сформированные замеры и события ошибок, проверять контракт, исключать повторную запись | US-06–07, US-12, NFR-07 |
| Измерения | Выдавать тестовую сессию, измерять download/upload и прикладной RTT с лимитами времени и трафика | US-17, NFR-11 |
| Оценка | Фильтровать, исключать повторы, рассчитывать достаточность и статус | US-08, NFR-08 |
| Модерация | Скрывать и восстанавливать записи с причиной | US-09 |
| Управление данными | Удалять собственные записи и аккаунт | US-10, NFR-05 |
| Справочники | Хранить операторов, профили задач и методику | US-02–03, US-14 |

Модульный монолит позволяет двум разработчикам запускать, тестировать и сопровождать один сервер. Разделение на модули сохраняет границы ответственности без отдельных сервисов, очередей и распределённых транзакций.

Правило взаимодействия слоёв:

```text
HTTP-контроллер → прикладной сервис → бизнес-правила → репозиторий → БД
```

Расчёт оценок не должен находиться в React-компонентах или HTTP-контроллерах.

Это предлагаемый стек. На момент проработки в репозитории находятся аналитические материалы, существующего UI kit нет.

Технические основания:

- [React: использование TypeScript](https://react.dev/learn/typescript).
- [NestJS: модульная организация](https://docs.nestjs.com/modules).
- [Яндекс Карты: полигоны и пример с React](https://yandex.ru/maps-api/docs/js-api/examples/cases/create-polygon.html).
- [PostGIS: пространственные индексы](https://postgis.net/documentation/faq/spatial-indexes/).

Для прототипа клиент работает через подменяемый адаптер данных. Сначала адаптер возвращает демонстрационные ответы, затем заменяется HTTP-клиентом с теми же контрактами. Интерфейс можно показать до завершения сервера. Прототип с имитацией входа не подтверждает выполнение требований безопасности и нагрузочных NFR.

Для карты необходимо получить API-ключ в кабинете Яндекса, настроить ограничения по доменам и передавать ключ через конфигурацию окружения. Условия использования и подходящий тариф проверяются перед публикацией. Карта отображает рассчитанные приложением статусы; фильтрация, агрегация и методика остаются в собственных модулях. Геокодер, поиск адресов и маршрутизация для текущего объёма не требуются. При недоступности API карты интерфейс показывает ошибку загрузки с повторной попыткой, не подменяя её отсутствием наблюдений.

### 3.1. Диаграмма вариантов использования

| Актор | Доступные действия |
|---|---|
| Гость | Смотреть карту, менять фильтры, выбирать профиль, открывать карточку, читать методику, запускать тест и отправлять наблюдение без привязки к пользователю |
| Участник | Все действия гостя; просматривать автоматически сохранённые события, смотреть и удалять свои записи, удалять аккаунт, выходить |
| Администратор | Действия участника; просматривать записи для модерации, скрывать и восстанавливать их, смотреть журнал |

На диаграмме участник наследует возможности гостя, администратор — участника.

Связи:

- «Запустить тест» включает получение доступных метаданных, измерение, проверку результата и автоматическое сохранение наблюдения.
- «Получить оценку зоны» включает проверку достаточности данных.
- «Скрыть запись» и «Восстановить запись» включают запись решения в журнал и обновление оценки.
- «Удалить свой вклад» включает проверку владельца и обновление оценки.

Вход требуется для `/me` и модерации. Создание тестовой сессии и публикация доступны гостю; технический токен попытки не является аккаунтом и не используется для идентификации человека.

### 3.2. Основной сценарий — выбрать место для видеозвонка

Дорожки: пользователь, интерфейс, сервер.

1. Пользователь открывает карту.
2. Интерфейс загружает пилотную территорию и справочники.
3. Пользователь выбирает оператора, сеть, период, условия и профиль «Видеозвонок».
4. Сервер формирует соответствующую выборку.
5. Сервер проверяет достаточность данных.
6. Если выборка достаточна — рассчитывает оценку; иначе возвращает серый статус с причиной.
7. Интерфейс показывает зоны.
8. Пользователь открывает карточку.
9. Карточка показывает показатели, период, число записей и ограничения оценки.

Результат: пользователь получает предварительную оценку либо понимает, почему её пока нет.

### 3.3. Сценарий администратора — модерация записи

Дорожки: администратор, интерфейс, сервер.

1. Администратор открывает раздел модерации; интерфейс запрашивает список записей.
2. Сервер проверяет сессию и роль. При отсутствии доступа интерфейс показывает отказ; при наличии — список записей с текущими статусами.
3. Администратор выбирает запись; интерфейс показывает её данные и текущий статус.
4. Администратор изучает запись, выбирает «Скрыть» или «Восстановить», указывает обязательную причину из справочника и применяет решение.
5. Сервер повторно проверяет права, причину и допустимость изменения текущего статуса. При отказе интерфейс показывает причину и не сообщает об успешном выполнении.
6. Сервер в одной транзакции сохраняет новый статус и решение в истории модерации: запись, действие, администратора, время и причину.
7. Если запись привязана к зоне, сервер пересчитывает её оценку по текущей методике. Скрытые записи исключаются; восстановленные проходят обычные правила отбора и достаточности данных.
8. Интерфейс показывает новый статус и подтверждение действия.

Результат: запись скрыта или восстановлена, решение доступно в истории модерации, оценка зоны обновлена при наличии привязки. Скрытие не удаляет исходные данные. Сценарий проверяет US-09, NFR-04, NFR-08 и NFR-09.

### 3.4. Исключение — ответ на отправку замера потерян

1. Гость или участник запускает тест; приложение автоматически формирует результат и сохраняет его в локальную очередь.
2. Клиент создаёт идентификатор операции и отправляет запрос.
3. Возможны две ветви: сервер успел сохранить запись либо запрос не дошёл.
4. Клиент не получает подтверждение.
5. Интерфейс сообщает: «Не удалось подтвердить отправку», сохраняя автоматически собранные данные.
6. Клиент повторяет отправку после восстановления доступа; пользователь также может нажать «Повторить».
7. Клиент использует тот же идентификатор операции.
8. Сервер возвращает уже созданную запись либо сохраняет её впервые.
9. Интерфейс показывает одно подтверждение.

Результат: повтор не создаёт дубль. Сценарий проверяет NFR-07.

| `methodology_versions` | `id PK`, `version UNIQUE`, `window_days`, `half_life_days`, `min_samples`, `min_dates`, `effective_from` |
| `task_profiles` | `id PK`, `methodology_id FK`, `code`, `name`, `min_download`, `min_upload`, `max_rtt` |
| `moderation_actions` | `id PK`, `observation_id FK`, `moderator_id FK`, `action`, `reason`, `created_at` |
| `idempotency_requests` | `id PK`, `attempt_id`, `attempt_token_hash`, `operation`, `key`, `payload_hash`, `result_id`, `created_at` |
| `deletion_events` | `id PK`, `target_type`, `target_id`, `requested_at`, `completed_at`, `purge_after` |

Связи для ER-диаграммы:

```text
users        1 ─── N sessions
users      0..1 ─── N test_sessions
test_sessions 1 ─── 0..1 measurement_details
test_sessions 0..1 ─── N complaint_details
users      0..1 ─── N observations
operators    1 ─── N observations
grid_cells   1 ─── N observations

observations 1 ─── 0..1 measurement_details
observations 1 ─── 0..1 complaint_details
observations 1 ─── N moderation_actions
users        1 ─── N moderation_actions

methodology_versions 1 ─── N task_profiles
attempt_id           1 ─── N idempotency_requests (техническая область повторов, не пользователь)
```

Для события ошибки ячейка и тестовая сессия могут отсутствовать, если их не удалось получить. Такое событие не публикуется на карте; количественный замер для карты требует ячейку и валидную тестовую сессию. Пара `identity_provider + provider_subject` уникальна.

Со стороны наблюдения связь с оператором необязательная: для неизвестного оператора `operator_id = NULL`.

На диаграмме коллекции связанных записей имеют кратность `0..N`: например, аккаунт может ещё не иметь наблюдений. `measurement_details.test_session_id` уникален, чтобы одна тестовая сессия соответствовала не более чем одному замеру. Событие ошибки может ссылаться на тестовую сессию, если она была создана. Для `idempotency_requests.result_id` и полиморфной пары `deletion_events.target_type + target_id` в текущей модели не заданы внешние ключи. Версия измерителя `method_version` отличается от версии методики оценки в `methodology_versions`.

Ограничения:

- У наблюдения существует ровно один соответствующий типу набор деталей. `attempt_id` уникален: одна попытка имеет один итог — замер либо событие ошибки.
- Неизвестный оператор — `NULL`, неизвестная технология — отдельное значение.
- Скорости и RTT неотрицательны; пропуск не равен нулю.
- Время события проверяется с заданным допуском расхождения часов.
- Комбинация `attempt_id + operation + key` уникальна; токен попытки проверяется до возврата сохранённой квитанции. `attempt_id` создаётся заново для каждого теста и не идентифицирует гостя.
- Причина модерации обязательна и выбирается из справочника без свободного текста.
- Точные пользовательские координаты в БД не поступают: браузер определяет ячейку до отправки.
- Сутки для исключения повторов считаются в зафиксированном часовом поясе пилота; сами моменты времени хранятся в UTC.

Журнал удалений нужен, чтобы после восстановления резервной копии повторно исключить удалённые данные. Его сроки хранения и очистку нужно согласовать с политикой резервных копий.

Агрегаты первоначально рассчитываются из наблюдений. Отдельный кэш вводится только при необходимости по результатам измерений. Это уменьшает риск расхождения карты и карточки.

## 5. Программные интерфейсы и контракты

Полное описание вынесено в [Программные интерфейсы взаимодействия компонентов](interfaces.md): границы компонентов, REST API, права, JSON-форматы, TypeScript-сигнатуры, сетка, идемпотентность и ошибки.

Базовый путь `/api/v1`. Гость и участник могут создавать тестовую сессию, выполнять измерение и отправлять результат. Сервер определяет необязательного автора из сессии входа при создании теста; клиент не передаёт `authorId`. Для гостя `test_sessions.user_id` и `observations.author_id` равны `NULL`. Токен отдельной попытки защищает измерительные endpoints и повторы, не связывает разные гостевые тесты и не заменяет пользователя.

Территория разбивается на квадраты 250×250 м в зафиксированной метрической проекции пилота. Клиент преобразует геолокацию в `cellId` до отправки. Размер согласован; город, проекция и начало сетки ещё выбираются. Геометрия для Яндекс Карт выдаётся в GeoJSON, координаты — долгота, широта.

Гостевые замеры участвуют в расчёте цвета наравне с замерами участников после общих проверок. Предлагаемая обновлённая методика: минимум 5 валидных тестовых сессий за 2 даты, без порога числа аккаунтов. Один результат на тестовую сессию; для известного автора сохраняется ограничение одного последнего валидного вклада за сутки в группе. Для гостя независимость авторов не подтверждается. Ограничения частоты не доказывают уникальность людей. Пороги требуют калибровки; версия методики меняется.

На смартфоне:

## 8. Архитектурные решения ADR

В задании итоговые ADR должны иметь статус «Принято». Сейчас их статус — «Предложено»; после согласования команда переводит их в «Принято».

### ADR-001: Модульный монолит для серверной части

**Статус:** Предложено.

**Контекст:** US-05–10 требуют связанных операций с аккаунтами, наблюдениями, модерацией и удалением. NFR-10 требует сопровождаемости. Команда состоит из двух разработчиков.

**Рассмотренные альтернативы:**

1. Микросервисы — увеличивают затраты на инфраструктуру и согласованность.
2. Единый сервер без модульных границ — затрудняет сопровождение.
3. Только клиент — не обеспечивает доверенную проверку прав.

**Принятое решение:** Предлагается один сервер с модулями авторизации, наблюдений, оценки, модерации и управления данными. Контроллеры вызывают сервисы, сервисы используют репозитории.

**Последствия:** Проще запуск и транзакции. Требуется соблюдать границы модулей. Масштабирование сначала выполняется для приложения целиком.

**Роль агента:** Агент предложил разбиение и сопоставил варианты с размером команды. Пользователь исключил ручной ввод и потребовал автоматическое заполнение; агент добавил измерительный модуль и очередь.

### ADR-002: React и TypeScript с подменяемым адаптером данных

**Статус:** Предложено.

**Контекст:** US-01–04 и US-11 требуют интерактивной карты и адаптивных экранов. ЛР 2 требует запускаемого прототипа с навигацией.

**Рассмотренные альтернативы:**

1. Статические HTML-страницы — сложнее поддерживать общие состояния.
2. Нативное приложение — расширяет объём разработки.
3. Приложение с серверным рендерингом — добавляет ненужный для выбранного прототипа слой.

**Принятое решение:** Предлагаются React-компоненты на TypeScript, доступ к данным через интерфейс адаптера и методика оценки в отдельном модуле.

**Последствия:** Автоматический сбор принят пользователем. Пригодность браузера для операторской карты остаётся условной до проверки метаданных. Интерфейс можно разрабатывать независимо от API. Нужно контролировать соответствие демонстрационного и HTTP-адаптеров. Локальная имитация ролей не обеспечивает безопасность.

**Роль агента:** Агент предложил разделить интерфейс, контракты и расчёт. Пользователь исключил ручные формы наблюдений; агент заменил их экраном теста и автоматическими состояниями. Выбор UI kit ещё не подтверждён.

### ADR-003: PostgreSQL с PostGIS и хранение ячеек вместо точных координат

**Статус:** Предложено.

**Контекст:** US-06–10 требуют связанных данных, агрегации, модерации и удаления. NFR-05 запрещает сохранение точных пользовательских координат.

**Рассмотренные альтернативы:**

1. JSON-файлы — неудобны для конкурентной записи и связей.
2. SQLite — допустим для локальной демонстрации, но для целевого многопользовательского сервера выбирается отдельная БД.
3. Документная БД — не даёт явного преимущества для этой связанной модели.

**Принятое решение:** Предлагаются реляционные таблицы наблюдений и их деталей, геометрия ячеек в PostGIS. Браузер отправляет `cellId`. Изменения схемы выполняются миграциями.

**Последствия:** Проще контролировать целостность. Требуется настройка БД и пространственной сетки. Ячейка снижает точность местоположения, но не доказывает полную анонимность.

**Роль агента:** Агент предложил модель и связал её с приватностью. Размер квадратов 250×250 м согласован. Выбор территории, метрической проекции и начала сетки остаётся за командой.

### ADR-004: REST API и идемпотентная запись наблюдений

**Статус:** Предложено.

**Контекст:** US-06–07 и NFR-07 требуют надёжной отправки при нестабильной сети. NFR-10 требует явных контрактов.

**Рассмотренные альтернативы:**

1. GraphQL — дополнительная сложность при небольшом числе операций.
2. WebSocket как основной транспорт — постоянное соединение не требуется.
3. POST без ключа операции — создаёт риск дублей после потери ответа.

**Принятое решение:** Предлагаются HTTPS, REST и JSON, OpenAPI, идемпотентный ключ для публикации, сохранение наблюдения и результата операции в одной транзакции.

**Последствия:** Повторная отправка предсказуема. Нужно хранить ключи, проверять содержимое повторов и определить срок их хранения. Конкурентные повторы требуют отдельного теста.

**Роль агента:** Агент предложил сценарий потери ответа и соответствующий контракт. Фактические результаты реализации и проверки дополнят ADR.

### ADR-005: Версионированная оценка и раздельный учёт событий ошибок

**Статус:** Предложено.

**Контекст:** US-03, US-04 и US-08 требуют объяснимой оценки. US-07 запрещает интерпретировать событие ошибки как нулевой замер. NFR-08 требует воспроизводимости.

**Рассмотренные альтернативы:**

1. Цвет по среднему download — игнорирует upload, RTT и достаточность.
2. Последняя запись — чрезмерно зависит от одного наблюдения.
3. Событие ошибки как нулевая скорость — искажает количественные данные.

**Принятое решение:** Предлагаются фильтрация по группе и периоду, исключение повторных вкладов, проверка достаточности и взвешенная доля замеров, прошедших профиль. События ошибок показываются отдельно. Ответ содержит версию методики и время расчёта.

**Последствия:** Результат можно объяснить и проверить. Необходимы тесты границ и старения. На старте карта может содержать много серых зон. Пороги требуют полевой калибровки.

**Роль агента:** Агент перенёс методику ЛР 1 в архитектурные правила и предложил проверочные наборы. Изменений порогов студентами пока нет.

## 9. Порядок выполнения и критерий готовности

1. Проверить доступность автоматических метаданных на целевых устройствах, выбрать способ входа без анкеты и демонстрационную территорию.
2. Оформить структурную схему, UML и ER-модель.
3. Согласовать wireframe-ы в команде.
4. Зафиксировать контракты и пять ADR.
5. Реализовать расчёт, симулятор измерений и демонстрационные данные; отдельно спроектировать реальный измерительный сервер для MVP.
6. Реализовать экраны и навигацию.
7. Проверить три сценария, пограничные данные, мобильную компоновку и клавиатуру.
